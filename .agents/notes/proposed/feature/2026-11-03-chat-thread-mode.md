# Agent Note: 会话窗口（对话式出图）

Status: proposed

## Problem

现在的创作页是单轮的：一句话 → 直接打图片模型。想做出满意的图，用户只能自己在脑子里改描述、反复重发，每次修改都要花掉一次图片额度。

对话式创作把"想清楚"和"出图"分开：先和语言模型聊，聊到描述满意了再出图。聊的轮次只走 chat 接口，不烧图片额度。

## Proposal

第三种创作模式并存，用户自己选，不替换现有创作页：

| 模式 | 说明 |
| --- | --- |
| 直接出图 | 现状不变 |
| 会话 | 左侧会话列表 + 右侧消息流，底部输入框 + 「用当前描述生成」 |

典型流程：用户说「我想做一张博客封面，猫的」→ 语言模型追问/给方案（不烧图片额度）→ 用户「第三版好，但它太亮了」→ 模型给出最终描述 → 用户点「用当前描述生成」→ 结果图回填到本轮会话。

### 意图判断：不赌模型

- **常驻按钮**：「用当前描述生成」永远可点；
- **模型标记**：规划回复可带 `readyToGenerate: true`，界面据此高亮按钮；
- 不靠模型猜"这句是不是要出图"——猜错要么白烧一张图，要么该出不出。

### 需要改动

1. **数据模型**：`ImageJob` 增加可选 `threadId`；新增轻量会话记录（标题、消息历史、产出的 assetIds），存 userData 并随数据导出。
2. **多轮对话**：现 `planPrompt` 是一次性请求，需要带历史消息；语言模型侧加 `chat(messages, signal)`。
3. **界面**：第三个导航项「会话」；左侧会话列表 + 右侧消息流；结果图作为一条消息显示。
4. **第二步才做**：`parentAssetId`，支持「在这张基础上改」——出图时把上一张作为参考图。

### 分两步

- 第一步：会话 + 多轮聊 + 手动/自动触发出图（不做参考图继承）；
- 第二步：`parentAssetId` + 参考图继承。

## Alternatives considered

- **把对话塞进现有创作页（一个输入框双模式）**：改动最小，不用新导航。但两套交互（一轮出图 vs 多轮商量）挤在同一个输入框里，用户无法预判这次回车会发生什么——正好违反上面"不赌意图"的原则。
- **让模型自己判断该不该出图（不要按钮）**：最"智能"。但误判代价不对称：多出一张图要花钱，少出一张图要重说一遍。按钮兜底是更稳的选择。
- **一次把 `parentAssetId` 也做掉**：一次成型。但参考图继承牵涉任务重放、遮罩与参考图上限的既有规则，和"先把会话跑通"不是同一量级的风险。
- **不做会话，只把提示词优化做深**：成本最低，复用现有 `optimizePrompt`。但那仍是单轮改写，回答不了"我想要 X 但说不清"的场景。

## Acceptance criteria

- 新建会话后可以多轮对话，每轮都不产生图片任务；
- 「用当前描述生成」始终可用；`readyToGenerate` 为真时按钮有明确高亮；
- 生成的任务带 `threadId`，结果图出现在对应会话的消息流里；
- 会话记录随数据导出/导入往返；老 job（无 `threadId`）不报错、不强行归入任何会话。

## Risks

- 老任务没有 `threadId`，会话表必须独立存储、不回填历史；否则导入旧备份时会炸。
- 会话多了列表需要分页或搜索，不能一次全渲染（与结果区时间线分页同一类问题）。
- 语言模型可用性决定这个模式是否可用：没有 chat 模型时「会话」入口要能优雅禁用，而不是让用户点进去发现发不出消息。
