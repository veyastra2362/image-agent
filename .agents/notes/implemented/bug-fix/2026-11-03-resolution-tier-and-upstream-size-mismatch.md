# Agent Note: 分辨率档位真正传到上游，长边收口到 4096

Status: implemented

## Problem

「画面」弹窗里的基准分辨率（1K / 1.5K / 2K / 4K）此前是**装饰品**：

- 渲染层把 `resolution` 放在 `OutputSpec` 里提交，但 `validateCreateJobInput` 的白名单没有这个字段，请求直接被拒（`请求包含未知字段：resolution`）；就算放行，`service.createJob` 里也写死 `DEFAULT_RESOLUTION = 1024`，比例模式永远按 1024 短边推导。
- 真实链路核对时又撞上第二个问题：16:9 选 4K → 请求 7280×4096 → 上游返回 4096×2305 → 严格相等校验判失败（`上游返回的尺寸 … 与请求的 … 不一致`）。

也就是说，用户看到的"将使用 7280×4096"从来没有被真的发出去过。

## Decision

1. `resolution` 成为一等字段：`ALLOWED_INPUT_KEYS` 放行、校验器只接受 1024/1536/2048/4096（其它值报错），校验结果带进 `CreateJobInput`；`service.createJob` 用它替换写死的 1024。
2. 比例模式的长边硬上限 `MAX_RATIO_LONG_EDGE = 4096`：由短边推导出的宽高若长边超限，**整体等比缩小**（比例不能改），16:9 的 4K 档因此请求 4096×2304。
3. 上游尺寸回显校验从"严格相等"放宽为"相差不超过 max(8px, 2%)"：取整误差（4096×2304 回显成 4096×2305）放行，比例被换掉或明显降档仍然报错。
4. 事后诊断保留：任务成功但尺寸与请求不符时，仍通过 `notify` 出一条 warning（任务详情里看得到）。

## Alternatives considered

- **把档位理解成"长边目标"**：语义上最贴近图上标注的"4K"。但 1:1 时两者等价，宽比例下短边会明显缩水（16:9 的 4K 只剩 2304 短边），而"基准分辨率"的既有文案是"短边 1024"，改成短边语义等于推翻已有文案。
- **保留严格相等校验，4K 直接报错让用户自己改档**：最诚实，但 1px 的取整误差就判失败，等于把上游的取整问题变成用户的问题。
- **按模型声明各自的最大边长**：最正确，但要给每个 provider/model 增加能力字段并维护，当前只有一个真机网关，投入产出不合算。
- **auto 模式兜底（不传尺寸，让上游自己定）**：能绕开所有尺寸问题，但用户选档位就没意义了。
- **对尺寸不符静默接受**：最省事，但"参数没生效"会被掩盖——这正是原来那条严格校验要防的事。

## Consequences

- 收益：档位真的生效（1024 → 1824×1024、2048 → 3640×2048、4K → 4096×2304，16:9），界面上的"将使用 …"与真正发出去的一致。
- 收益：取整误差不再把任务判死；真正被上游改尺寸时仍有 warning 可查。
- 代价 1：`MAX_RATIO_LONG_EDGE` 是全局常量，不是模型能力。将来接支持 8K 的服务商，这里会成为误伤点。
- 代价 2：长边收口让"4K"在宽比例下短边不足 4096（16:9 只有 2304），文案"4K 超清"略有夸张，接受。
- 代价 3：容差 2% 让"上游悄悄降了 1.5%"这种情况不会被拦，只在任务详情里 warning。

## Testing

- 单测：`src/test/image-openai-provider.test.ts` 新增「尺寸只差取整误差时放行」（请求 4096×2304，回显 4096×2305 → 成功）；原有「尺寸不一致时明确报错」（请求 1024×1024，回显 512×512 → 拒绝）保持通过。
- 端到端（假服务，只验证尺寸推导链路）：`resolution` 1024/2048/4096 + 16:9 → `requestedSize` 分别为 1824×1024 / 3640×2048 / 4096×2304。
- 真实链路（网关可用时）：JPEG 与 WebP 已验证 —— 请求 1K，落盘 `image/jpeg` / `image/webp`（本机转码生效，10KB 级别）；同一网关对 1K PNG 也返回 1254×1254 并走 warning，属上游行为，不在本应用修。
